# Frontend setup

Two independent TanStack Start apps share `packages/ui` and `packages/data`. Orchestrator (admin/instructor) runs on port 5000; learner runs on port 5001. Development and preview commands use strict ports: if a port is occupied, startup fails instead of silently switching ports. The sibling backend is not part of this monorepo.

## Shared UI

Generated with `shadcn init --preset b7nwSN6jVA --template start --monorepo --pointer`. Base UI/Vega styling, neutral surfaces and purple shared theme remain intact. Both apps use the supplied Season Collection Sans for body text, headings and controls: `SeasonCollectionVF-TRIAL.ttf` has a Sans axis value of `SERF: 0` and variable weights 300-900. Each app serves its own identical public asset and preloads it; the shared CSS uses `font-display: swap` and system sans fallbacks. The supplied file is a trial; confirm an appropriate webfont license before public deployment. Orchestrator auth uses a scoped blue accent and a compact, centered form inspired by the supplied reference. Its light and dark colors are semantic tokens; light is the default even when the OS prefers dark. Both apps use a shared theme provider and theme switch; `martyrs.theme` stores the preference. A pre-paint script avoids a light flash when dark is saved. Phosphor replaces the preset's Lucide selection, as requested; all three `components.json` files agree. The root icon provider sets size 20 and regular weight. Import icons individually from `@phosphor-icons/react/dist/csr/<Icon>` to avoid compiling the whole icon collection in development.

Add components from either app with `npx shadcn@latest add <component> -c apps/orchestrator` (or `apps/learner`). Aliases route shared UI into `packages/ui`; use its semantic tokens and components rather than duplicate app-local controls. The pointer-button CSS generated by the preset is preserved.

## Apollo and TanStack Query

Apollo owns GraphQL operations, normalized entities and mutation cache updates. Hooks come from `@apollo/client/react`; route loaders can use `context.preloadQuery`. The official TanStack Start adapter provides Apollo's streaming SSR hydration. Its installed version is `0.14.5-rc.0`, pinned deliberately; review adapter upgrades.

TanStack Query owns REST and other non-GraphQL requests. Use `context.queryClient.ensureQueryData(...)` in loaders and Query hooks in components. The router SSR Query adapter handles dehydration, hydration and provider wrapping. Do not wrap the same GraphQL data in a second Query cache.

Each `getRouter()` creates fresh clients, never process-wide instances. Both integrations preserve existing router wrapping and serialization; the caches are separate per request and per app. Typed starter documents match the backend's current `health` and `me` operations. Full schema-based GraphQL code generation is deferred.

## Endpoint and authentication boundary

Each app's `.env.example` documents `VITE_GRAPHQL_URL`, defaulting to `http://localhost:4000/graphql`. It must be an absolute HTTP(S) URL reachable from both browser and SSR server. `VITE_*` values are public build-time configuration, never a place for credentials. The HTTP health check derives `/health` from the backend origin.

The Apollo HTTP link sends `credentials: "include"` and reads bearer tokens dynamically. `createDataClients().setAccessToken(token)` supplies an in-memory token and clears both caches on identity change/logout. Nothing persists tokens in browser storage. The optional `getAccessToken` callback supports a future request-local SSR session and takes precedence over that setter.

Orchestrator sign-in calls `login`; admin/instructor results populate a router-scoped in-memory session and bearer token. Learner accounts are refused by this app and their newly issued refresh cookie is revoked through `logout`. `/workspace` checks the session and displays a minimal signed-in handoff, not a completed dashboard. Sign-out calls `logout` before clearing both caches and in-memory identity. Forgot-password uses `requestPasswordReset` with an enumeration-safe confirmation; reset-password reads the email link's fragment token and calls `resetPassword`.

"Remember my email" persists only the email on this browser origin. It does not imply persistent sign-in: refresh coordination, session restoration after reload/expiry, authenticated SSR, Google callback handling and invitation acceptance are **not implemented**. Reloading a protected route returns to sign-in. The backend refresh cookie is not an access token; protected operations require a valid bearer JWT. Never serialize tokens into router context, share a server-global token, or forward incoming cookies to an untrusted endpoint.

Backend local/default CORS settings permit `http://localhost:5000` and `http://localhost:5001`. `APP_URL` uses `http://localhost:5000` for existing auth redirects and email links. Configure the exact deployed origins before launch. Local ports do not isolate cookies: both apps can share the backend cookie namespace on localhost. Choose a deliberate session/domain strategy in the identity slice before supporting simultaneous different identities.

## Forms

All current forms (orchestrator sign-in, forgot-password, reset-password) use Formik and Yup. Learner has no forms yet; both apps have these dependencies for future features. Feature schemas live in `apps/orchestrator/src/auth/validation.ts`, matching backend email/password bounds. Login accepts existing short passwords; new passwords require 12-128 characters and matching confirmation. Password values are never trimmed. Emails are normalized at the API boundary.

Reuse `@workspace/ui/components/form-input` inside `FormikProvider`: `FormInput` connects native inputs to Formik, touched inline errors, and accessible descriptions; `FormFeedback` displays server errors and focuses a navigable summary on failed submit. Use `Form` with `noValidate`, keep default change/blur/submit validation, and guard submission while `isSubmitting`. Errors appear after touch/submission and disappear as fields are corrected. Keep server errors in Formik `status`, not field validation errors. Validation regression tests run with `npm test`.

The form refactor passed all workspace typechecks/lint, six auth-schema tests plus five data-client tests, and both client/SSR builds. Browser checks with mocked GraphQL covered invalid submissions making no requests, accessible error descriptions/summary focus, API-error retry, pending duplicate guards, email normalization/remembering, password confirmation, reset-fragment cleanup, default light, and dark/mobile layout. Live authentication and email delivery remain unverified.

## Starter checks and scope

The learner starter retains a manual check for Apollo GraphQL `health` and Query HTTP `/health`. Orchestrator now opens the auth UI. Nothing contacts the backend automatically during SSR. These public checks do not prove authenticated workflows or provider integration.

From the root: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. Focused tests cover cache isolation, credential inclusion, token rotation/logout, endpoint validation and mutation retry defaults. Build outputs include client and SSR bundles; choose/configure an appropriate hosting adapter before production deployment.

Next slice: refresh/session coordination, Google callback and invitation acceptance, then orchestrator authoring/review and learner course journeys. The auth UI is not a completed identity lifecycle or product dashboard.

## Frontend structure

```text
apps/<app>/src/
  router.tsx              # Request-local clients and SSR integrations
  root.tsx                # Root route and full HTML document
  route-tree.tsx          # Explicit createRoute / addChildren declarations
  route-definitions.ts    # Typed path constants / build asset metadata
  pages/                  # PascalCase route view components
packages/data/
  src/                    # Shared clients, REST helpers, exports and tests
  apollo/
    auth/query.ts         # Auth queries and mutations
    platform/query.ts     # Health query
tooling/programmatic-start.mts
```

File-route generation is disabled in both Start plugins. There are no `createFileRoute`, generated route trees or route-generation scripts. Start's current build internals still consume `TSS_ROUTES_MANIFEST`, normally populated by its file-route generator. Our small Vite compatibility plugin supplies that asset metadata from each app's explicit route definitions. It does not generate or replace the runtime route tree. SSR and both Apollo/Query hydration adapters remain enabled. This is an internal compatibility point: use the lockfile and recheck production SSR, hydration and asset links on every Start upgrade. New routes must be added to the explicit tree and its metadata. File-based automatic route splitting is not active; add deliberate lazy page loading as the apps grow.
