# Frontend setup

Two independent TanStack Start apps share `packages/ui` and `packages/data`. Orchestrator (admin/instructor) runs on port 3000; learner runs on port 5173. The sibling backend is not part of this monorepo and is unchanged.

## Shared UI

Generated with `shadcn init --preset b7nwSN6jVA --template start --monorepo --pointer`. Base UI/Vega styling, neutral surfaces, purple theme, Inter body text and Instrument Sans headings remain intact. Phosphor replaces the preset's Lucide selection, as requested; all three `components.json` files agree. The root icon provider sets size 20 and regular weight. Import icons individually from `@phosphor-icons/react/dist/csr/<Icon>` to avoid compiling the whole icon collection in development.

Add components from either app with `npx shadcn@latest add <component> -c apps/orchestrator` (or `apps/learner`). Aliases route shared UI into `packages/ui`; use its semantic tokens and components rather than duplicate app-local controls. The pointer-button CSS generated by the preset is preserved.

## Apollo and TanStack Query

Apollo owns GraphQL operations, normalized entities and mutation cache updates. Hooks come from `@apollo/client/react`; route loaders can use `context.preloadQuery`. The official TanStack Start adapter provides Apollo's streaming SSR hydration. Its installed version is `0.14.5-rc.0`, pinned deliberately; review adapter upgrades.

TanStack Query owns REST and other non-GraphQL requests. Use `context.queryClient.ensureQueryData(...)` in loaders and Query hooks in components. The router SSR Query adapter handles dehydration, hydration and provider wrapping. Do not wrap the same GraphQL data in a second Query cache.

Each `getRouter()` creates fresh clients, never process-wide instances. Both integrations preserve existing router wrapping and serialization; the caches are separate per request and per app. Typed starter documents match the backend's current `health` and `me` operations. Full schema-based GraphQL code generation is deferred.

## Endpoint and authentication boundary

Each app's `.env.example` documents `VITE_GRAPHQL_URL`, defaulting to `http://localhost:4000/graphql`. It must be an absolute HTTP(S) URL reachable from both browser and SSR server. `VITE_*` values are public build-time configuration, never a place for credentials. The HTTP health check derives `/health` from the backend origin.

The Apollo HTTP link sends `credentials: "include"` and reads bearer tokens dynamically. `createDataClients().setAccessToken(token)` supplies an in-memory token and clears both caches on identity change/logout. Nothing persists tokens in browser storage. The optional `getAccessToken` callback supports a future request-local SSR session and takes precedence over that setter.

Login, refresh coordination, authenticated SSR, role guards and unauthorized recovery are **not implemented**. The backend refresh cookie is not an access token; protected operations require a valid bearer JWT. Never serialize tokens into router context, share a server-global token, or forward incoming cookies to an untrusted endpoint.

Backend example CORS settings already permit `http://localhost:3000` and `http://localhost:5173`. Configure the exact deployed origins before launch. Local ports do not isolate cookies: both apps can share the backend cookie namespace on localhost. Choose a deliberate session/domain strategy in the identity slice before supporting simultaneous different identities.

## Starter checks and scope

Each app has a manual check for Apollo GraphQL `health` and Query HTTP `/health`. Nothing contacts the backend automatically during SSR. Failures show an unavailable state, not simulated success. These public checks do not prove authenticated workflows or provider integration.

From the root: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. Focused tests cover cache isolation, credential inclusion, token rotation/logout, endpoint validation and mutation retry defaults. Build outputs include client and SSR bundles; choose/configure an appropriate hosting adapter before production deployment.

Next slice: invitation/login/refresh and role-aware routes, then orchestrator authoring/review and learner course journeys. This scaffold does not claim completed product screens.

### Scaffold validation

Verified on Node 24.15.0: all four workspace typechecks and lint tasks, five data-client tests, and both client/SSR production builds. Headless Chrome checked both preview apps at desktop and 390px mobile widths, including hydration, no automatic backend fetch, unavailable/retry states, and explicitly mocked Apollo/HTTP success. No live authenticated-backend integration was verified. Builds currently emit a non-failing warning for the roughly 578 kB uncompressed entry chunk; revisit route/vendor chunking as product screens are added.
