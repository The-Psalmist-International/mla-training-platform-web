# Frontend setup

Two independent TanStack Start apps share `packages/ui` and `packages/data`. Orchestrator (admin/instructor) runs on port 5000; learner runs on port 5001. Development and preview commands use strict ports: if a port is occupied, startup fails instead of silently switching ports. The sibling backend is not part of this monorepo.

Both apps use the supplied Season Collection Sans for body text, headings and controls: `SeasonCollectionVF-TRIAL.ttf` has a Sans axis value of `SERF: 0` and variable weights 300-900. The supplied file is a trial; confirm an appropriate webfont license before public deployment. A pre-paint script avoids a light flash when dark is saved. Phosphor replaces the preset's Lucide selection, as requested; all three `components.json` files agree. The root icon provider sets size 20 and regular weight. Import icons individually from `@phosphor-icons/react/dist/csr/<Icon>` to avoid compiling the whole icon collection in development.

Add components from either app with `npx shadcn@latest add <component> -c apps/orchestrator` (or `apps/learner`). Aliases route shared UI into `packages/ui`; use its semantic tokens and components rather than duplicate app-local controls. The pointer-button CSS generated by the preset is preserved.

## Apollo and TanStack Query

Apollo owns GraphQL operations, normalized entities and mutation cache updates. Hooks come from `@apollo/client/react`; route loaders can use `context.preloadQuery`. The official TanStack Start adapter provides Apollo's streaming SSR hydration. Its installed version is `0.14.5-rc.0`, pinned deliberately; review adapter upgrades.

TanStack Query owns REST and other non-GraphQL requests. Use `context.queryClient.ensureQueryData(...)` in loaders and Query hooks in components. The router SSR Query adapter handles dehydration, hydration and provider wrapping. Do not wrap the same GraphQL data in a second Query cache.

Each `getRouter()` creates fresh clients, never process-wide instances. Both integrations preserve existing router wrapping and serialization; the caches are separate per request and per app. Typed documents and operation types are generated from the sibling backend's `schema.graphql`; no live endpoint is needed.

## GraphQL code generation

Operations live in `packages/data/apollo/<feature>/query.graphql`; each feature's
`query.ts` reexports generated typed documents and compatibility aliases. The
features are `course`, `media`, `enrollment`, `assessment`, `submission`, `people`,
`invitation`, `certificate`, `email-delivery`, `auth`, and `platform` (health only).
Import through `@workspace/data` or `@workspace/data/apollo/<feature>/query`.
Existing root operation/type exports and auth mutations are preserved.

Keep `../mla-platform-core/schema.graphql` current using the backend's codegen
workflow. From the frontend root or `packages/data`, run:

```sh
npm run codegen
npm run codegen:check
```

`codegen.ts` resolves absolute paths relative to the config, so both working
directories use the same schema, feature documents, and output. Commit
`packages/data/src/generated/graphql.ts` after changing documents or the schema;
do not edit or format it manually. `codegen:check` validates operations and fails
on stale output without writing. Use it as an optional CI validation; ordinary
data typecheck/tests do not regenerate or require a running backend.

Generated types follow SDL rather than backend validators: nullable inputs such
as course `mine` allow null, while email `purpose`/`EmailDeliveryPurpose` are
strings. Omit unset filters and retain backend-specific validation in callers.
Pagination still uses non-null inputs with the existing operation defaults.

## Shared data tables

The optional `layout` prop controls presentation: omit it (or use `{ mode: "table" }`) for the default cell table; use `{ mode: "grid", renderCard }` for grid-only; use `{ mode: "toggle", renderCard }` to show the table/grid controls with table as the default. Toggle mode supports either internal state with an optional `defaultView`, or controlled `view` and `onViewChange` for URL-backed state. Grid/toggle modes require a feature-owned `renderCard(row)`. Search, filters, refresh, scroll region, totals, and pagination are shared across both presentations. Grids use semantic lists, responsive columns, card skeletons, and the same empty/error states. Switching layout does not change the requested rows or pagination.

Courses and Video library now use this component with a table/grid toggle. They start in table view; `layout=grid` restores the card layout. Their URLs also hold `q`, `status`, `page`, `pageSize`, and course `scope=mine|all`. The generated `CoursesPage` and `MyVideoAssetsPage` queries provide server-side search/filtering and matching totals, preserving course visibility and owner-only lesson-video access. Instructors default to their own courses; All accessible courses also includes other published courses. With no course status filter, archived courses remain excluded, matching the existing catalog contract. Layout is omitted from data query keys so switching views does not fetch a different page. Search/filter/page-size changes reset the page; changing layout preserves it.

Grid cards follow the supplied preview/title/description layout with shared theme tokens. Current course/video records expose no cover/thumbnail URLs, so the preview panel uses a neutral course/video icon instead of fabricated imagery. Course descriptions and video duration/size/type are real API data. Course curriculum authoring and cover-image support remain separate work; metadata/lifecycle actions and video upload/preview are integrated. Deploy the backend exposing the new page queries alongside this frontend; these queries add no database columns or migrations.

Pagination is always URL state. Current page, page size, and filters/selections affecting the list must be read from validated route search parameters, rather than stored only in component state. Defaults may be omitted from the URL when validation restores them deterministically. People and Invitations use their feature validators; shared collection routes use `page`, `pageSize`, and `course`, with offsets derived from the URL and page size included in query cache keys. Course changes reset the page while preserving page size. Back/Forward and direct links restore the same list parameters.

`packages/ui/src/components/data-table.tsx` provides a controlled, native-table layout: search on the left, entity filters on the right, and a table panel that fills the available workspace height even when it has few rows. Rows scroll inside the borderless panel under a rounded, muted sticky header, with subtle alternating row shading instead of divider lines. The full-width pagination footer remains outside the row scroll area, with a “Showing X to Y out of Z” summary on the left, outlined First/Previous/Next/Last controls centered, and a compact “N / page” select on the right; narrow panels wrap navigation onto a centered second row. Columns, rows, filters, search, and pagination callbacks belong to each feature. Every table requires an `onRefresh` callback and shows an outlined refresh icon beside its filters (also when no filters exist); it stays still and is disabled while loading/fetching. Loading uses full-width, column-aligned skeleton rows instead of centered bars. Shared `SelectInput` uses Base UI, a custom caret, styled options, keyboard navigation, and selected-item indicators for filters/page sizes. It reuses shared Input/Button controls and accepts shared loading, empty, and error states; no table-library dependency is required.

People is the first implementation. Its Name cell combines an initials avatar, name, and email; account status uses the shared `StatusBadge` with semantic success colors in both themes. “Created at” displays the actual `createdAt` date and time in UTC (identified by the timestamp's title). Icon actions offer role changes and account enable/disable through centered confirmation modals using Formik/Yup. Shared `Dialog` is the default for forms and confirmations unless a drawer is explicitly requested; the mobile sidebar remains a navigation drawer. These call `setUserRole` / `setUserDisabled`, revoke the target's sessions, and refresh all cached People pages/filters. Changing one's own access clears the local session immediately. The backend's last-active-administrator safeguard is shown as an actionable error; it is not inferred from a paginated list. No unsupported delete action is offered. It uses the admin-only `usersPage` query with name/email search, role and active/disabled filters, page size, offset, and a matching `totalCount`. Search is debounced by 300 ms; filter/page-size changes reset to the first page. Validated route search parameters (`q`, `role`, `status`, one-based `page`, `pageSize`, `modal`, `person`) preserve table and modal state through navigation. Defaults and invalid values fall back safely; typing replaces the current history entry, while page/filter/modal changes create entries for Back/Forward. Modal URLs contain only an ID and action type; form values and person details are not serialized. A selected person is restored from the requested page, with loading/unavailable states instead of invented profile lookup endpoints. Navigation is blocked during access mutations. Existing in-memory session limitations still apply to full page reloads. Filtering is server-side across all people, not just the visible page. The existing `users` query is unchanged. Deploy/restart the updated backend alongside this page so `usersPage` is available. Generated types have been regenerated from the updated schema.

## Course and video library actions

Create course and Upload video actions in the header and empty states now open shared dialogs. Validated library URLs preserve filters, pagination, and layout alongside `modal`/`item` selection. New/create/upload dialogs need no ID; edit/details/publication/archive/resume/preview dialogs restore the selected record by UUID through independent queries, even when it is not on the current list page. Form values, files, request keys, upload signatures, and player tokens are not serialized into the URL. Completing an action refreshes all library list variants and relevant detail queries without losing table state. Empty/error content is centered across the full table cell, with the same centered grid state.

Course metadata forms use Formik/Yup for title, description, and certificate preference. Drafts support editing and publishing; published courses can return to draft; non-archived courses can be archived after confirmation. Only owners/admins see management controls, with backend authorization and publication readiness checks remaining authoritative. Details show the description and current section/item outline. Full curriculum/assessment authoring and owner assignment are separate workflows; this slice does not bypass publication requirements or delete course history.

Video upload uses `createLessonVideoUpload`, then `tus-js-client` sends the file directly to Bunny with the short-lived signed target. Create retries keep the same request key and inputs unless the backend confirms a terminal creation failure. Upload progress, pause, and retry preserve the selected file in the open dialog; closing/unmounting aborts transfer without terminating the provider record. Across reloads, use the existing row's Resume upload action and choose the original file. TUS fingerprints are scoped by user/asset/file metadata so one upload cannot resume another video. Expiring credentials are renewed through `refreshLessonVideoUpload`; file bytes/signatures are sent only to the expected Bunny TUS destination. SDK URL storage contains recovery metadata, never backend API keys or access tokens. A successful byte transfer triggers `syncLessonVideoAsset`; failed status refresh is reported separately from upload success. Encoding readiness is read from the backend, not inferred from 100% transfer progress.

Video details provide manual status checks, and ready videos have signed previews from `previewLessonVideo`. Previews accept only the provider's HTTPS embed host, expire visibly, and can be refreshed; signed player URLs are not retained in the Apollo cache or URL state. Provider credentials remain backend configuration. Contract/transport tests use mocked API/TUS responses; they do not prove actual file transfer, encoding, dashboard security, or playback against live Bunny. Verify a real upload/webhook/ready/preview flow before provider-completion claims.

## Invitation management

Administrators can manage invitations at `/workspace/invitations`. The table uses `invitationsPage` for server-side email search, role/status filters, pagination, and matching totals, ordered newest first. Statuses are pending, accepted, revoked, and expired; accepted takes precedence over revoked, and expiration uses the current time. Created/expiry timestamps are displayed in UTC. Search, filters, page size, and create/resend/revoke dialogs are represented by validated URL parameters (`q`, `role`, `status`, `page`, `pageSize`, `modal`, `invitation`). Form values and invitation tokens are never written into URLs. Row dialogs restore their selection from the current page and show loading/unavailable states when it cannot be restored.

The header and empty-state Invite people actions open the create dialog. Formik/Yup validates and normalizes email and role. Sending/resending calls `createInvitation`; resending creates a replacement with the same email/role and invalidates earlier pending links. Accepted invitations have no actions; pending invitations can be revoked, and expired/revoked invitations can be resent. Mutations block duplicate submissions and navigation, retain input on errors, and refresh all invitation table filters/pages after success. `EMAIL_QUEUE_UNAVAILABLE` means the invitation was saved but its email was not queued: the dialog stays open with retry instructions and the table refreshes. Success confirms queueing, not actual delivery; delivery diagnostics remain on Email delivery.

Deploy/restart the updated backend with the frontend so `invitationsPage` is available. No schema migration is needed for this query. Invitation acceptance screens and live email-provider verification remain separate work.

## Endpoint and authentication boundary

Each app's `.env.example` documents `VITE_GRAPHQL_URL`, defaulting to `http://localhost:4000/graphql`. It must be an absolute HTTP(S) URL reachable from both browser and SSR server. `VITE_*` values are public build-time configuration, never a place for credentials. The HTTP health check derives `/health` from the backend origin.

The Apollo HTTP link sends `credentials: "include"` and reads bearer tokens dynamically. `createDataClients().setAccessToken(token)` supplies an in-memory token and clears both caches on identity change/logout. Nothing persists tokens in browser storage. The optional `getAccessToken` callback supports a future request-local SSR session and takes precedence over that setter.

Orchestrator sign-in calls `login`; admin/instructor results populate a router-scoped in-memory session and bearer token. Learner accounts are refused by this app and their newly issued refresh cookie is revoked through `logout`. `/workspace` checks the session before entry and reactively redirects to sign-in when the session clears. Login's `expiresIn` drives a browser expiry timer, with deadline checks on route access and tab return. Apollo `UNAUTHENTICATED` or HTTP 401 responses for the current token clear the session; ordinary network failures and `FORBIDDEN` do not. Responses belonging to an older login cannot invalidate a newer session. Identity is cleared immediately, before cache cleanup; sign-out clears local state even if the logout endpoint is unavailable. Forgot-password uses `requestPasswordReset` with an enumeration-safe confirmation; reset-password reads the email link's fragment token and calls `resetPassword`.

"Remember my email" persists only the email on this browser origin. It does not imply persistent sign-in: refresh coordination, session restoration after reload/expiry, authenticated SSR, Google callback handling and invitation acceptance are **not implemented**. Reloading a protected route returns to sign-in. The backend refresh cookie is not an access token; protected operations require a valid bearer JWT. Never serialize tokens into router context, share a server-global token, or forward incoming cookies to an untrusted endpoint.

Backend local/default CORS settings permit `http://localhost:5000` and `http://localhost:5001`. `APP_URL` uses `http://localhost:5000` for existing auth redirects and email links. Configure the exact deployed origins before launch. Local ports do not isolate cookies: both apps can share the backend cookie namespace on localhost. Choose a deliberate session/domain strategy in the identity slice before supporting simultaneous different identities.

## Frontend structure

```text
apps/<app>/src/
  router.tsx              # Request-local clients and SSR integrations
  root.tsx                # Root route and full HTML document
  route-tree.tsx          # Explicit createRoute / addChildren declarations
  route-definitions.ts    # Typed path constants / build asset metadata
  pages/                  # PascalCase route view components
packages/data/
  src/                    # Shared clients, REST helpers, exports and tests
    generated/graphql.ts  # Generated schema/operation types and typed documents
  apollo/<feature>/
    query.graphql         # Source operations (platform: health; auth: existing flows)
    query.ts              # Typed document reexports and derived type aliases
codegen.ts                # Local sibling schema and feature document configuration
tooling/programmatic-start.mts
tooling/vendor-chunks.mts  # Shared client-only vendor splitting
```

File-route generation is disabled in both Start plugins. There are no `createFileRoute`, generated route trees or route-generation scripts. Start's current build internals still consume `TSS_ROUTES_MANIFEST`, normally populated by its file-route generator. Our small Vite compatibility plugin supplies that asset metadata from each app's explicit route definitions. It does not generate or replace the runtime route tree. SSR and both Apollo/Query hydration adapters remain enabled. This is an internal compatibility point: use the lockfile and recheck production SSR, hydration and asset links on every Start upgrade. New routes must be added to the explicit tree and its metadata.

### Programmatic route-level lazy loading

Both explicit route trees use `lazyRouteComponent(() => import("./pages/PageName"), "PageName")` for page views. This keeps each page behind a dynamic import while preserving named exports, programmatic `createRoute` declarations, and SSR. Route matching, redirects, workspace authorization, and head metadata stay eager in the route tree; only view components are lazy. Router intent preloading remains enabled, so hovering/focusing a link can deliberately load its page before navigation.

Use this pattern for new pages and add their metadata to `route-definitions.ts`. Do not add eager imports of these pages elsewhere, which can defeat splitting. Shared framework/data clients and auth-form dependencies may remain eagerly loaded or shared across chunks; route splitting does not automatically reduce all initial downloads or remove vendor-size warnings. File-based automatic splitting remains disabled.

Verified after splitting: all workspace typechecks/lint, 11 tests, and both client/SSR builds passed. Production browser checks confirmed selected-route SSR/hydration, recovery navigation, authenticated workspace/sign-out navigation, and that unvisited page chunks are not fetched on sign-in. The workspace guard redirects before downloading the denied page. Auth regression responses were mocked. Main chunks decreased from approximately 716 to 528 kB (orchestrator) and 647 to 580 kB (learner); both still emit size warnings. These are main-chunk sizes, not total cold-load transfer savings: active views also download shared/page dependencies.

### Targeted vendor splitting

Both apps use the shared `targetedVendorChunks()` Vite plugin in `tooling/vendor-chunks.mts`. It configures only the client build through `build.rolldownOptions.output.codeSplitting`, grouping React/React DOM, TanStack/serialization, and Apollo/GraphQL/RxJS. Groups are entry-aware, so consumers don't automatically download vendor modules used only by other routes. Dependencies aren't recursively absorbed into groups; page code, Formik/Yup, icons, and UI utilities retain automatic splitting. Module execution order is preserved for safe initialization across chunks. SSR build configuration and the default chunk-size warning threshold are unchanged.

Production builds now finish without oversized-chunk warnings. Largest client chunks are approximately 212 kB for orchestrator and 220 kB for learner, compared with 528/580 kB before vendor splitting. This improves chunk boundaries and caching opportunities, not total first-load size: splitting and execution-order wrappers add some bytes and requests. Production hosting should serve hashed assets with long-lived caching while keeping HTML fresh and retaining old assets across deployments. No hosting cache policy was changed here.

`npm test` now includes three tooling regression tests for client-only configuration, package boundaries on Windows/POSIX, and keeping application/forms/icons outside targeted groups, alongside the existing 11 tests.

Vendor-split verification passed workspace typechecks/lint, all 14 tests, and both client/SSR production builds with no chunk-size warnings. Browser checks passed vendor initialization, selected-route SSR/hydration, unvisited-page lazy boundaries, login failure/retry, duplicate guards, workspace/sign-out, password recovery/reset, authentication redirects, mobile/theme behavior, and learner hydration. GraphQL auth responses were mocked; this is not live provider or deployed-cache verification.
